## 缺陷 1：小额订单永远不收运费

- **位置**：`server.mjs` 第 **455** 行，`handleCheckout()` 内：
  ```js
  // 【缺陷 1】响应里的 shipping 被写死为 0
  const shipping = 0
  ```
- **正确规则**：`subtotal >= 99` 免运费，否则收 10 元（`calcShipping()` 已实现正确规则，第 120 行）。
- **实际表现**：无论订单金额多少，响应里的 `shipping` 恒为 `0`。
- **影响**：所有未满 99 元的订单少收 10 元运费，`total` 随之偏低，公司直接亏钱；
  下游按 `total` 对账、开票都会跟着错。
- **应失败用例**：`小额订单应收取运费`（`p1001` 无线耳机 ×1，小计 59.9）
  - 断言 `$.shipping equals 10` → 实际 `0` ❌
- **修复建议**：`const shipping = calcShipping(subtotal)`。

## 缺陷 2：优惠券折扣的基数把运费也算进去了

- **位置**：`server.mjs` 第 **460–461** 行，`handleCheckout()` 内：
  ```js
  // 【缺陷 2】折扣基数错误地使用了 (subtotal + 真实运费)
  const discountBase = subtotal + calcShipping(subtotal)
  const discount = couponCode === 'SAVE10' ? round2(discountBase * 0.1) : 0
  ```
- **正确规则**：`SAVE10` = 对**商品小计**打 9 折，即 `discount = round2(subtotal * 0.1)`。
- **实际表现**：小计 59.9 时折扣算成 `(59.9 + 10) × 0.1 = 6.99`，而不是 `5.99`。
- **影响**：每笔用券订单多打 1 元折扣（运费越高偏差越大），且折扣与商品金额脱钩，
  财务对账时「折扣 + 实付 ≠ 小计」。
- **应失败用例**：`优惠券应按商品小计计算折扣`
  - 断言 `$.discount equals 5.99` → 实际 `6.99` ❌
- **修复建议**：`const discount = couponCode === 'SAVE10' ? round2(subtotal * 0.1) : 0`。

> **关于题面的一处内在矛盾（已做取舍）**
> 题面同时要求「`shipping` 永远返回 0」和「`discount` 按 `(subtotal + shipping) * 0.1` 计算」。
> 如果把运费在内部也固定成 0，两式恒等（`(subtotal+0)*0.1 === subtotal*0.1`），
> **缺陷 2 在数值上永远观测不到**，「优惠券」用例就无法失败，与题面「该用例应失败」冲突。
> 因此本实现把运费拆成两处，两个缺陷都真实可观测：
> 内部 `calcShipping()` 仍按正确规则算出真实运费（10 元），只是被折扣错误地当成了基数；
> 而**响应字段** `shipping` 被写死为 0。这样：
> - 「`shipping` 响应字段永远是 0」→ 缺陷 1 成立，用例 6 失败；
> - 「折扣按 `(subtotal + shipping) × 0.1` 计算」→ 缺陷 2 成立，用例 7 失败。

## 缺陷 3：下单完全跳过库存校验（超卖）

- **位置**：`server.mjs` 第 **445–446** 行，`handleCheckout()` 遍历购物车的循环里，
  本该有校验的位置只留了一句注释：
  ```js
  // 【缺陷 3】这里应当校验库存：qty > product.stock 时返回
  //   400 { error: '库存不足' }。示例软件故意跳过了这段校验。
  ```
- **正确规则**：`qty > product.stock` 时返回 `400 { error: '库存不足' }`。
- **实际表现**：库存只有 10 件的商品可以一次下单 9999 件，接口返回 `200` 并生成订单。
- **影响**：**超卖**。库存 10 卖出 9999 件，后续要么发不出货、要么强制退款，
  属于电商最严重的一类资损缺陷；并发场景下还会被放大。
- **应失败用例**：`库存不足应拒绝下单`
  - 断言 `status equals 400` → 实际 `200` ❌
  - 断言 `$.error equals 库存不足` → 实际取不到该字段 ❌
- **修复建议**：在循环内补上
  ```js
  if (qty > product.stock) { sendJson(res, 400, { error: '库存不足' }); return }
  ```

## 缺陷 4（前端）：结算只显示整数金额，且不显示运费行

- **位置**：`server.mjs` 第 **310–313** 行，`shopPage()` 生成的商城页内联 JS 的 `checkout()` 里：
  ```js
  // 【缺陷 4】前端只把 total 的整数部分渲染出来，而且完全不显示运费行。
  var shown = Math.trunc(Number(r.data.total));
  box.textContent = '合计：' + shown + ' 元';
  ```
- **正确实现**：显示 `data.total.toFixed(2)`（例如「合计：52.91 元」），并渲染运费明细行。
- **实际表现**：服务端返回 `total: 52.91`，页面却显示 **「合计：52 元」**；购物车里也没有运费行。
- **影响**：用户看到的应付金额比实际少了零头，属于**价格展示不一致**；
  与「运费」相关的信息在前台完全缺失，用户无法在付款前知道运费。
- **应失败用例**：`结算合计金额显示正确`（加入 1 件无线耳机 + 优惠券 SAVE10 后结算）
  - 断言「元素文本包含 `合计`」→ ✅ 通过（文案是对的）
  - 断言「元素文本匹配正则 `\d+\.\d{2}`」→ ❌ 失败（页面只有 `52`，没有两位小数）
- **修复建议**：`box.textContent = '合计：' + Number(r.data.total).toFixed(2) + ' 元';`
  并补一条运费行（例如 `data-testid="shipping-row"`）。

## 怎么用这些缺陷演示「修复 → 回归」

1. 启动被测服务与平台，导入 `cases.json`，执行全部用例 → 看到 **7 通过 / 4 失败**。
2. 按上面「修复建议」逐个改 `server.mjs`（每次只改一处），重启被测服务，只跑 `bug` 标签的用例。
3. 4 处全部修好后，11 个用例应全部通过；此时 `node code/examples/demo-app/selfcheck.mjs` 里
   标着「【缺陷 N 复现】」的检查会**反过来失败**——这正是「缺陷已修好」的信号。

> 自检脚本 `selfcheck.mjs` 断言的是「缺陷按文档描述存在」，所以它在**未修复**状态下才全绿。
