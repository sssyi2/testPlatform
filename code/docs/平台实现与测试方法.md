# 平台实现与测试方法说明

这份文档回答两个问题：**这个测试平台是怎么实现的**，以及**它支持/使用了哪些测试方法**。
所有结论对应仓库里的真实代码，文件路径都可直接点开核对。

---

## 一、整体架构（怎么实现的）

### 1. 分层

```
┌──────────────────────────────────────────────────────────────┐
│ 界面层  code/web/            React + Vite + TypeScript 单页应用 │
│   项目栏 / 用例列表 / 表单化用例编辑器 / 执行面板 / 历史与报告    │
└───────────────┬──────────────────────────────────────────────┘
                │ REST + SSE（原生 fetch / EventSource，无第三方库）
┌───────────────▼──────────────────────────────────────────────┐
│ 服务层  code/server/src/index.mjs     node:http，零框架         │
│   路由 / 校验 / 静态托管 / SSE 推送 / 报告导出 / 导入导出        │
├──────────────────────────────────────────────────────────────┤
│ 编排层  runner.mjs                    执行生命周期 + 事件广播    │
│   选例 → 起浏览器 → 逐例执行 → 汇总 → 落盘 → 广播 → 清理       │
├──────────────────────────────────────────────────────────────┤
│ 执行器（适配器）                                               │
│   runners/api.mjs   HTTP/API 用例                              │
│   runners/web.mjs   Playwright/Chromium Web UI 用例            │
├──────────────────────────────────────────────────────────────┤
│ 引擎层  assertions.mjs（断言）   vars.mjs（变量/取值/抽取）      │
├──────────────────────────────────────────────────────────────┤
│ 数据层  store.mjs   JSON 文件（原子写 + 串行化），无数据库       │
│   data/db.json（项目+用例）  data/runs/<runId>.json（结果）     │
│   data/runs/<runId>/（截图等产物）                              │
└──────────────────────────────────────────────────────────────┘
```

### 2. 技术选型与理由

| 选择 | 理由 |
| --- | --- |
| 后端零框架（`node:http` + 自写 100 行路由） | 平台自身依赖越少越可信；沙箱/内网环境下装不上依赖也能跑 |
| 变量/断言/报告全部自研 | 断言语义要中文可读、要能解释"期望 vs 实际"，现成框架不易定制 |
| JSON 文件存储（原子写 + 串行队列） | 无需数据库进程；数据可整体拷贝、可人工查阅 |
| SSE（`EventSource`）而不是 WebSocket | 测试执行是**单向**推送，SSE 更简单且自带断线重连 |
| Playwright + Chromium（装在工作区内） | 真实浏览器才能测出前端缺陷；装在 `code/.playwright-browsers` 不污染系统 |
| React + Vite + TS | 用例编辑器表单复杂，组件化 + 类型约束能少踩坑 |

### 3. 关键文件职责

| 文件 | 职责 |
| --- | --- |
| `server/src/index.mjs` | 服务入口：REST 路由、请求校验、静态托管、SSE 端点、报告、导入导出、示例清单 |
| `server/src/runner.mjs` | 执行编排：选例、并发模型、事件广播、历史回放、取消、汇总、xfail 判定 |
| `server/src/runners/api.mjs` | API 执行器：拼 URL/头/查询/请求体、超时、流式限长读响应、变量抽取、断言 |
| `server/src/runners/web.mjs` | Web 执行器：浏览器生命周期、10 种页面动作、元素解析、断言、失败截图 |
| `server/src/assertions.mjs` | 断言引擎：10 种断言类型 × 11 种比较符，数值感知比较，中文失败说明 |
| `server/src/vars.mjs` | 变量插值 `{{var}}`、内置动态变量、JSONPath 取值、正则抽取 |
| `server/src/store.mjs` | 数据层：读改写串行化、原子写、执行记录与产物目录 |
| `server/src/report.mjs` | 自包含 HTML 报告（截图内联 base64、结论徽标、汇总卡片） |
| `server/src/http.mjs` | 极简 HTTP 工具：路由匹配、JSON body、静态文件、SSE 封装 |
| `web/src/*` | 界面：项目/用例管理、表单化用例编辑器、执行面板、历史与报告 |

### 4. 一次执行的数据流（时序）

```
界面点「运行全部启用」
   │ POST /api/runs {projectId, caseIds?, tags?, variables?}
   ▼
runner.startRun()  选出用例 → 建 run 记录（状态 running）→ 立即返回 runId
   │ （后台异步执行，HTTP 请求不阻塞）
   ├─ 有用例是 web 类型？→ launchBrowser()（一次 run 复用一个 Chromium）
   ├─ emit run:start
   └─ 逐个用例（顺序执行）：
        ├─ emit case:start
        ├─ 合并变量：内置 → 运行级 → 用例级；baseUrl 优先级 用例级 > 运行级 > 项目
        ├─ api: fetch（AbortController 超时）→ 流式读响应(上限 2MB) → 抽取变量 → 逐条断言
        │  web: 每例独立 context → 执行动作 → 按断言自带 selector 解析元素 → 断言 → 失败截图
        ├─ 计算 verdict（含 xfail/xpass）→ 更新 summary → 落盘 runs/<id>.json
        └─ emit case:end
   ▼
执行结束 → emit run:end → 汇总 →（历史保留 10 分钟供晚订阅者回放）

界面 EventSource 订阅 /api/runs/:id/events
   首帧 snapshot（当前状态+已完成用例明细）→ 回放已发生事件（标 replay:true）
   → 实时事件：run:log / step:log / assertion / step:end / case:end …
```

### 5. 几个实现上的关键决定

- **顺序执行而非并发**：测试结果的可解释性优先（日志、共享变量、同一浏览器上下文），
  避免并发带来的相互干扰；需要并发时可以起多个 run。
- **SSE 历史回放**：订阅发生在 POST 之后，早期事件可能错过；因此编排层保留每个 run 的事件历史
  （上限 3000 帧 / 10 分钟），订阅时先推 snapshot 再回放，保证界面状态一致。
- **失败即证据**：Web 用例失败自动截图，报告把截图内联成 base64，单个 `.html` 就能当证据归档。
- **协作式取消**：`cancelRun` 置标记，当前用例跑完即停（不硬中断请求），界面会提示"等待当前用例结束"。
- **契约稳定**：事件类型、字段名是对外契约（`case:start` 的用例类型字段叫 `caseType`，
  不能叫 `type`，否则会覆盖事件判别字段——这是踩过的坑）。

## 二、平台支持哪些测试方法（重点）

平台不是"只发个请求看状态码"，它覆盖了下列测试方法/技术，每条都有对应落地实现与示例用例。

| # | 测试方法 | 平台怎么落地 | 代码位置 | 示例用例 |
| --- | --- | --- | --- | --- |
| 1 | **冒烟测试** | 用例打 `smoke` 标签，`POST /api/runs {tags:["smoke"]}` 只跑冒烟集 | `runner.startRun` 的 tags 过滤 | 健康检查、登录成功、搜索商品 |
| 2 | **接口/功能测试** | 请求编排 + 多维断言（状态码、JSONPath、响应体、响应头、耗时） | `runners/api.mjs` + `assertions.mjs` | 8 个 API 用例 |
| 3 | **端到端 UI 测试** | Playwright 驱动真实 Chromium：goto/fill/click/select/press/hover/check/waitForSelector/waitForTimeout/screenshot | `runners/web.mjs` | 登录→商城、搜索过滤、结算 |
| 4 | **负向测试** | 断言"应该失败"的路径：401、404、400 及错误文案 | 同 2 | 登录失败 401、商品不存在 404、库存不足 400 |
| 5 | **边界值分析** | 针对阈值设计用例：99 元免运费的门槛、优惠券折扣基数、库存上限 | 示例用例设计（`cases.json`） | 小额订单运费（59.9 < 99）、库存 9999（> 10） |
| 6 | **等价类划分** | 合法/非法凭据、存在/不存在的资源分成等价类各测一条 | 示例用例设计 | 登录成功 vs 登录失败；商品详情 vs 不存在 |
| 7 | **场景/链路测试（有状态）** | 多步骤用例 + 变量抽取：登录取 `token`，后续步骤带 `Authorization: Bearer {{token}}` | `runners/api.mjs` 的 `runExtracts` | 运费/折扣/库存三条都是"先登录再下单" |
| 8 | **数据驱动测试** | `{{变量}}` 插值 + 三级覆盖（项目/用例/运行级）+ 内置动态变量 `{{$timestamp}} {{$isoDate}} {{$date}} {{$uuid}} {{$randomInt}}` | `vars.mjs` | 所有用例都用 `{{baseUrl}}`、`{{username}}` |
| 9 | **回归测试** | 执行历史（`data/runs/`）+ 可重复执行 + 一键导出报告对比 | `store.listRuns`、`report.mjs` | 每次改完被测软件重跑全部用例 |
| 10 | **已知缺陷管理（xfail/xpass）** | 用例级 `expectedFailure`：失败记 xfail（不判定整体失败），反而通过记 xpass（提示缺陷可能已修） | `runner.verdictOf` / `summarize` | 可在演示时把 4 条 bug 用例标成"预期失败" |
| 11 | **轻量性能测试** | `responseTime` 断言（`lt/lte/gt/gte`），可设单步超时 | `assertions.mjs` | 健康检查断言"响应 < 3 秒" |
| 12 | **证据留痕 / 可追溯** | 失败截图、步骤日志、请求/响应快照、自包含 HTML 报告、原始事件流 | `runners/web.mjs`、`report.mjs` | 结算金额错的失败截图 |
| 13 | **契约测试** | 对平台自身的 SSE 事件契约做校验（事件齐全、顺序正确） | `tools/sse-contract.mjs` | 见第四节 |
| 14 | **变异测试思想** | 被测示例软件故意植入 4 个缺陷（变异体），验证平台**能否发现**——能发现才说明用例有效 | `examples/demo-app/BUGS.md` | 4 条 bug 用例全部失败 = 变异被杀死 |
| 15 | **测试分层（金字塔）** | 脚本级自测（快）→ 端到端验收（全）→ UI 冒烟（真实浏览器点界面） | `tools/selftest.mjs` / `verify-all.mjs` / `ui-smoke.mjs` | 见第四节 |

> 说明：方法 5/6/14 属于**用例设计技术**，由用例本身体现（示例用例就是这么设计的）；
> 其余是平台**提供的能力**。这样区分，是为了回答"平台能做什么"和"这套示例怎么用平台"两个不同问题。

### 断言能力清单

10 种断言类型：

| 类型 | 适用范围 | 说明 |
| --- | --- | --- |
| `status` | API | 响应状态码 |
| `jsonPath` | API | 取 JSON 里的值（`$.data.items[0].name`）后比较 |
| `bodyContains` / `bodyMatches` | API | 响应体包含文本 / 匹配正则 |
| `headerContains` | API | 响应头包含指定值 |
| `responseTime` | API | 响应耗时（毫秒）比较 |
| `urlContains` | Web | 当前地址包含 |
| `elementVisible` | Web | 元素可见 |
| `elementText` | Web | 元素文本 |
| `elementCount` | Web | 元素数量 |

11 种比较符：`equals` `notEquals` `contains` `notContains` `matches` `gt` `gte` `lt` `lte` `exists` `truthy`。
其中 `equals` 是**数值感知**的：`"200"` 与 `200` 视为相等，避免 JSON 数字/字符串差异造成假失败。

### 用例的声明式结构（DSL）

用例 = 元信息 + 步骤序列；每个步骤可带请求/动作、断言、变量抽取：

```jsonc
{
  "name": "小额订单应收取运费", "type": "api", "tags": ["order", "bug"],
  "steps": [
    { "name": "先登录拿令牌",
      "request": { "method": "POST", "url": "{{baseUrl}}/api/login",
                   "bodyMode": "json", "body": "{\"username\":\"{{username}}\",\"password\":\"{{password}}\"}" },
      "extract": [{ "name": "token", "from": "json", "path": "$.token" }],
      "assertions": [{ "type": "status", "op": "equals", "expected": 200 }] },

    { "name": "结算一件 59.9 元商品",
      "request": { "method": "POST", "url": "{{baseUrl}}/api/cart/checkout",
                   "headers": { "Authorization": "Bearer {{token}}" },
                   "bodyMode": "json", "body": "{\"items\":[{\"productId\":\"p1001\",\"qty\":1}]}" },
      "assertions": [
        { "type": "status",   "op": "equals", "expected": 200 },
        { "type": "jsonPath", "op": "equals", "path": "$.shipping", "expected": 10,
          "name": "小额订单运费应为 10 元" }
      ] }
  ]
}
```

Web 用例把 `request` 换成 `action`（见方法 3 的 10 种动作），断言换成元素类断言。

## 三、示例软件为什么"必须有缺陷"

`code/examples/demo-app/` 是一个零依赖的"小商城"，**故意**植入 4 个缺陷
（`BUGS.md` 里有文件行号与修复建议）：

| # | 缺陷 | 应该被哪条用例抓到 |
| --- | --- | --- |
| 1 | 小额订单运费恒为 0（漏收 10 元） | 小额订单应收取运费 |
| 2 | 优惠券折扣基数含运费（6.99 ≠ 5.99） | 优惠券应按商品小计计算折扣 |
| 3 | 跳过库存校验（9999 件也能下单） | 库存不足应拒绝下单 |
| 4 | 前端合计只显示整数（52 ≠ 52.91） | 结算合计金额显示正确（Web） |

这就是**变异测试**的思路：把"植入的缺陷"当作变异体，如果用例集抓不到它们，说明用例无效。
实测结果是 4 条全部失败 → 4 个变异体全部被杀死。

## 四、平台自身是怎么被验证的（元测试）

平台自己也要被测，否则"测试结果可信"无从谈起。验证分四层（下表的数字是 **2026-09-23 复跑**的真实结果）：

| 层 | 工具 | 做什么 | 实测 |
| --- | --- | --- | --- |
| 1. 契约层 | `tools/sse-contract.mjs` | 校验 SSE 事件契约：`run:start → case:start → step:start → step:log/assertion → step:end → case:end → run:end` 齐全且顺序正确 | 契约齐全 ✅ |
| 2. 集成层 | `tools/selftest.mjs` | 一个进程内拉起示例软件 + 平台，导入示例 → 执行全部用例 → 校验断言/截图/报告/xfail 语义 | **12 项检查全绿** |
| 3. 端到端层 | `tools/verify-all.mjs` | 上面两层 + 真实浏览器界面验收，一次性给结论 | **API 12 项 + 界面 10 项全绿** |
| 4. 界面层 | `tools/ui-smoke.mjs` | 用 Playwright **去点平台自己的界面**：导入示例 → 运行全部 → 看实时日志 → 打开报告，逐步截图 | **10 项全绿**，6 张截图 |
| 附：被测软件侧 | `examples/demo-app/selfcheck.mjs` | 示例软件自己的自检（契约 + 接口 + 页面选择器 + 缺陷复现 + 用平台执行器离线跑 API 用例） | **63 项符合预期，0 项不符** |

**最近一次完整验收的真实输出**（`node tools/verify-all.mjs`，2026-09-23）：

```
11 个用例 · 通过 7 · 失败 4 · 异常 0 · 耗时约 2.9 s
✅ 执行流程跑通   ✅ 能测出被测软件缺陷   ✅ Web 用例产生截图证据
✅ 预期失败用例记为 xfail 且不影响结论
界面自测 10 项：界面可打开并渲染 / 点击导入示例 / 用例列表已渲染 / 触发执行 /
              执行已结束 / 被执行的目标服务可达 / 失败信息在界面可见 / 报告可打开 / 刷新无异常
```

失败明细正是那 4 个植入缺陷（期望 vs 实际逐条给出），例如
`期望等于 10，实际 0`、`期望匹配正则 /\d+\.\d{2}/，实际 合计：52 元`。

产物位置：`code/data/runs/<runId>.json`（结构化结果）、`code/data/runs/<runId>/*.png`（截图）、
`code/data/reports/*.html`（可独立打开的报告）、`code/data/ui-shots/*.png`（界面验收截图）。

## 五、怎么扩展（加一种新测试类型）

执行器是**适配器模式**，加类型只需三步（以"命令行程序测试"为例）：

1. 写 `server/src/runners/cli.mjs`，导出 `runCliCase(testCase, options)`，
   返回与 API/Web 执行器**同构**的结果对象（`{caseId, name, type, status, durationMs, steps[], screenshots[]}`），
   并在步骤里 `emit` 事件（`step:start` / `step:log` / `assertion` / `step:end`）。
2. 在 `runner.mjs` 的用例分发处加一个分支（`testCase.type === 'cli' ? runCliCase(...) : ...`）。
3. 在 `assertions.mjs` 里按需补 `scope: 'cli'` 的断言类型（如 `exitCode`、`stdoutContains`），
   并在界面 `CaseEditor` 的动作/断言下拉里出现（界面是按 `scope` 动态过滤的，不需要改界面代码）。

数据模型、报告、SSE、历史记录都无需改动。

## 六、局限与不做的事（避免误解）

- **不是**分布式压测工具：并发压力测试不在范围内，`responseTime` 只是轻量耗时断言。
- **不是**单元测试框架：平台测的是"运行中的软件"（HTTP 接口 / 网页 / 进程），不负责注入到被测代码内部改写桩。
- **不识别图片型验证码 / 复杂桌面应用**：Web 用例依赖 DOM 选择器；桌面程序需要另写执行器。
- **顺序执行**：单次 run 内用例串行；大规模并行需要起多个 run 或后续加入调度层。
- **JSON 存储**：适合单机/小团队；多人并发写需要换成真正的数据库（数据层已隔离在 `store.mjs`，替换成本低）。
- **示例软件的缺陷是刻意植入的**：它的失败是**预期基线**，不代表平台有 bug。
