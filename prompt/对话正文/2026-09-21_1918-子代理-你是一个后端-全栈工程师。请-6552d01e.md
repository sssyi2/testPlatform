# 一、被测软件（虚构的「小商城」）
`server.mjs` 同时提供 REST API 和少量服务端渲染的 HTML 页面（用于浏览器自动化测试）。

## REST API（前缀 `/api`，全部返回 JSON，UTF-8）
- `GET /api/health` → `{ status: 'ok', time }`
- `POST /api/login` body `{username, password}`：
  - 正确账号：`admin/123456`、`alice/alice123`
  - 成功 → `200 { token, user: { id, name, role } }`（token 用 `crypto.randomUUID()`，并在内存里记住）
  - 失败 → `401 { error: '用户名或密码错误' }`
- `GET /api/products?keyword=` → `{ items: [{id, name, price, stock}], total }`（keyword 为空返回全部；匹配 name 包含关键字；**至少 5 件商品**，价格用「元」为单位的数字，如 `price: 59.9`）
- `GET /api/products/:id` → 商品对象；不存在 → `404 { error: '商品不存在' }`
- `POST /api/cart/checkout`（需要请求头 `Authorization: Bearer <token>`，缺失/无效 → `401`）body `{ items: [{productId, qty}], couponCode? }` →
  `{ orderId, items, subtotal, shipping, discount, total, createdAt }`
- `GET /api/orders/:orderId`（需要 token）→ 订单；不存在 → `404`
- `GET /api/orders`（需要 token）→ `{ items: [...] }`（当前用户的订单）
- `GET /api/echo?status=500&body=xxx` → 调试用：按 query 返回指定状态码与响应体（方便平台演示各种断言）

## 结算金额规则（**这是故意埋缺陷的地方，必须严格按此实现**）
- `subtotal` = 各商品 `price * qty` 之和（保留 2 位小数）
- 正常规则应为：`subtotal >= 99` 时运费 0，否则运费 10
  - **缺陷 1**：实现里 `shipping` 永远返回 `0`（漏算了小额订单的 10 元运费）。→ 用例「小额订单应收取运费」会失败。
- 优惠券 `SAVE10` 应为「对 `subtotal` 打 9 折」（`discount = subtotal * 0.1`）
  - **缺陷 2**：实现里 `discount` 按 `(subtotal + shipping) * 0.1` 计算。→ 用例「优惠券应按商品小计计算折扣」会失败。
- 库存校验：`qty > stock` 应返回 `400 { error: '库存不足' }`
  - **缺陷 3**：实现里完全跳过库存校验，照样下单成功。→ 用例「库存不足应拒绝下单」会失败。
- `total` = `subtotal + shipping - discount`（保留 2 位小数）
- 未登录下单必须 401；订单保存进内存数组。

## HTML 页面（供 Playwright 使用，**必须带稳定选择器**）

## 五、平台上手体验建议

- **先只跑 `smoke` 标签**（全绿）再跑 `bug` 标签（4 红），失败与通过的对比最直观，适合录制演示视频。
- **把「失败是预期」讲清楚**：建议在用例名/描述里保留「（此处会失败）」，报告里 4 条红就是预期基线；`BUGS.md` 的「修复 → 回归」章节可直接当演示脚本（改一处 → 只跑 bug 标签 → 变绿）。
- **踩到的平台细节值得写进平台文档**：Web 的 `elementText/elementVisible/elementCount` 断言的元素来自**步骤的 `action.selector`**（断言自带 `selector` 会被忽略），两者必须一致，否则断言永远取不到元素 —— 我已在 `selfcheck.mjs` 里做成校验规则，建议平台在用例编辑器里加同样的告警。
- 建议平台在「导入示例」列表里显示 `readme`（已有）并加「预期结果」提示（如「7 通过 / 4 失败」），新手才知道红色不是平台坏了。
- 建议给「预期失败」加一等公民支持（如用例级 `expectedFailure`/`known_bug` 标签），否则一份健康的含缺陷样例报告永远是红的，不利于 CI 判定。
